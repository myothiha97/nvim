# Neovim config — working notes for AI agents

> **IMPORTANT**: Do NOT edit this file unless the user explicitly asks to.
>
> This is the canonical reference for how this repo works. `docs/AGENTS.md`
> points here; do not duplicate content into it, or the two will drift.
>
> Read `rules.md` and `neovim-config-change-gate.md` at the repo root FIRST.
> They decide *whether* a change should happen. This file only describes *how*
> to make one once it has passed that gate.

## Architecture

- LazyVim-based config on the `main` branch (uses `nvim-treesitter` main branch API)
- `init.lua` boots through `lua/config/lazy.lua`
- Editor-wide behaviour in `lua/config/` (`options.lua`, `keymaps.lua`, `autocmds.lua`)
- Plugin specs and overrides in `lua/plugins/`, usually one file per plugin.
  Disabled specs are kept on purpose as a record of what was rejected and why
- Colorschemes in `lua/colorschemes/`; the active one is chosen in `config.lua`.
  The solarized-osaka theme is a package: `lua/colorschemes/solarized-osaka/`
  with `init.lua` (the spec and highlight overrides), `palette.lua` (colour
  values by role) and `variants.lua` (the switchable builds)
- Custom snippets (VSCode JSON format) in `snippets/`; `snippets/package.json`
  registers them
- `scripts/palette/` holds measuring tools for the syntax colours. Nothing there
  runs at startup

## Performance Rules

- All changes MUST be performance-safe. No heavy per-keystroke computations.
- Silently ensure performance safety — do NOT remind the user about performance checks unless there is an actual issue.
- Before committing, always review ALL changed files for performance safety (no per-keystroke work, no expensive autocmds, no blocking operations)
- Prefer in-process solutions (snippets, treesitter) over external LSP servers when possible
- Disabled plugins for performance: nvim-lint, bufferline, persistence, mini.ai, treesitter-context, flash, harpoon, spectre, avante, sidekick, telescope
- noice: ENABLED but cut back to the cmdline popup only (messages, popupmenu, notify and all LSP handlers off)
- gitsigns: ENABLED (replaced neogit), `LazyFile`-deferred load, signs/hunks only, `current_line_blame` off for perf
- Lualine throttled to 400ms statusline refresh (tabline/winbar 1000ms)

## Build, test and development commands

- `XDG_STATE_HOME=/tmp/nvim-state XDG_CACHE_HOME=/tmp/nvim-cache nvim --headless '+qa'`
  checks the config boots without touching your normal Neovim state.
- `nvim` launches the config for manual smoke testing.
- `:Lazy sync` refreshes plugins after editing specs or `lazy-lock.json`.
- `stylua --check init.lua lua` verifies Lua formatting from `stylua.toml`;
  `stylua init.lua lua` rewrites to the repo style.
- `:checkhealth` for plugin, LSP or provider issues.

Note that `nvim -l script.lua` does **not** load this config — no lazy.nvim, no
colorscheme — so any measurement taken that way is silently wrong. Use
`nvim --headless -c 'lua …' -c 'qa!'` instead.

## Coding style and naming

Lua is formatted with Stylua: spaces, 2-space indent, 120-column width. Follow
LazyVim conventions — return plugin specs from `lua/plugins/*.lua`, keep comments
brief and purposeful, prefer descriptive file names tied to a feature or plugin.

Comments should explain *why*, and especially what NOT to do: most of the long
comments in this repo exist because an obvious-looking fix was tried and failed.
Preserve that reasoning when editing around it.

## Completion (blink.cmp)

- Sources: lsp (score 100), snippets (score 90), path, buffer
- Tab/S-Tab unbound (use Enter to accept, Ctrl-n/p to navigate)
- Ghost text disabled
- Completions disabled in comments and Avante buffers
- Emmet LSP only for HTML files (NOT for TSX/JSX - causes unwanted suggestions)
- Bracket-only completions from emmet are filtered out
- Do NOT override snippets provider `opts.search_paths` - blink.cmp defaults already include `~/.config/nvim/snippets/`

## Snippets

- Use blink.cmp built-in snippets provider (NOT LuaSnip)
- VSCode JSON format in `snippets/` directory
- `package.json` maps snippet files to filetypes
- Do NOT use nested tabstops like `${1: className='$2'}` - causes LSP snippet grammar errors
- Keep snippet files minimal - only add frequently used patterns
- Snippets config consolidated in `performance.lua` (not separate snippets.lua)

## LSP

- emmet_ls: HTML only (not TSX/JSX)
- eslint: disabled (TypeScript sufficient)
- vtsls: TypeScript LSP with 200ms debounce
- Custom `gd` mapping filters out node_modules

## Treesitter

- textobjects configured via `nvim-treesitter-textobjects` plugin (NOT through nvim-treesitter opts)
- LazyVim only auto-creates keymaps for `move` - `select` keymaps (af/if/ac/ic/aa/ia) MUST be created manually via lazy.nvim `keys` spec
- Uses LazyVim's `keys` property under `move` for buffer-local keymaps
- `[f`/`]f` navigation handled by textobjects, NOT custom keymaps in keymaps.lua
- Custom queries live in `after/queries/<lang>/highlights.scm` with `; extends`.
  They are how a capture gets split when a highlight group alone cannot express
  it — see the logical-operator files for the pattern

## Syntax colours

Do not change a colour without reading `notes/syntax-palette-decisions.md`
first. Every rejected candidate is recorded there with a dated reason, and most
obvious ideas have already been measured and rejected. `scripts/palette/README.md`
covers the measuring tools and how to read the numbers.

## Terminal and keybinding context

Primary usage is macOS + Ghostty + tmux. Review `~/.config/ghostty/config` and
`~/.tmux.conf` alongside Neovim keymap changes. Ghostty keeps
`macos-option-as-alt = false`, sends Meta through explicit `super+...=esc:...`
bindings, and maps `ctrl+i` to CSI-u so `<C-i>` stays distinct from `<Tab>`.
tmux enables `extended-keys`, `escape-time 0`, and `focus-events on`, with
`Ctrl+Space` as prefix. Smoke-test `<C-i>`, `<Tab>`, `<M-/>`, `<M-f>`, `<M-i>`
and pane resize shortcuts after input-related edits.

Ghostty also runs `window-colorspace = display-p3`, which means authored colour
values are not what the panel emits. That matters for any theme work.

## Testing

There is no automated test suite. Validate by starting Neovim, exercising the
affected workflow, and checking for startup errors or regressions. For plugin,
completion, formatting or LSP changes, do a manual pass over the related feature
and run `:Lazy sync` when specs changed.

## Committing

- When asked to commit, automatically load the `/perf-review` skill to analyse the changes for performance safety
- Only proceed to commit if the changes pass that check
- Never edit directly on `main` — branch, verify, merge back
- Conventional commit prefixes: `feat:`, `fix:`, `perf:`, `refactor:`, `chore:`,
  `docs:`. Keep subjects short, imperative and scoped to one change, e.g.
  `fix: resolve prettierd fallback`. No `Co-Authored-By` line
- Pull requests should summarise the behaviour change, list touched modules,
  include manual verification steps, and add screenshots when floats, themes or
  statusline behaviour change
