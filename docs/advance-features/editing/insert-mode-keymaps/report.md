# Leave insert mode; map two keys at most

Experienced Vim and Neovim users mostly do not navigate in insert mode. They make Esc cheap (Caps Lock, `<C-[>`, `<C-c>` or `jk`), move with normal-mode motions, and re-enter with `i`/`a`/`A`/`I`/`o`. Inside insert mode they use the built-in editing keys (`<C-w>`, `<C-u>`, `<C-h>`, `<C-r>`) and an occasional `<C-o>` for a single normal-mode command. Custom Alt/Ctrl+hjkl motion maps are a tolerated minority habit, usually justified by one narrow case: stepping past an auto-inserted closing bracket. For this user, Esc is already a single Caps Lock tap, and Cmd+key arrives in Neovim as the same bytes as Esc+key. That removes most of the benefit of insert-mode motion maps and keeps all of their costs. The recommendation is **Option C (defer) now, honouring the freeze**, plus a no-config habit change: Caps-Esc and normal mode for any real movement, and built-in insert keys for small fixes. If a specific pain is still there when the freeze ends, the most worth adding is a **two-key, cut-down version of Option A**: Cmd+H/L as `<C-g>U<Left>`/`<C-g>U<Right>`, with only Copilot's accept-line moved. **Option B should be rejected** in either case.

## Authorities and starter configs agree on "normal mode is home"

Vim's own user manual, written by Bram Moolenaar, treats Esc → motion → re-enter as the default. It says "you usually leave Insert mode with <Esc>, execute the Normal mode command, and re-enter Insert mode", and presents `CTRL-O` as "a quicker way" for **one** command ([usr_24.txt](https://vimhelp.org/usr_24.txt.html)). The manual also assesses arrow-key correction inside insert mode directly. It calls that the modeless-editor style, "easier to remember, but takes more time", and "most useful when writing a mapping that doesn't leave Insert mode" ([usr_24.txt](https://vimhelp.org/usr_24.txt.html#24.1)). Drew Neil's *Practical Vim* calls normal mode "Vim's natural resting state" ([O'Reilly, Ch. 2](https://www.oreilly.com/library/view/practical-vim-2nd/9781680501629/f_0025.xhtml)). Its insert-mode tips cover corrections (`<C-h>`, `<C-w>`, `<C-u>`), fast exits (`<C-[>`), `<C-o>` as "Insert Normal mode", and `<C-r>` pasting, but **not cursor navigation** ([Tip 14](https://www.oreilly.com/library/view/practical-vim-2nd/9781680501629/f_0034.xhtml)). Tom Ryder lists moving in insert mode as an anti-pattern because "that's what normal mode is for", and adds that leaving insert mode keeps inserts "more *atomic*, and hence more useful to repeat" ([sanctum.geek.nz](https://blog.sanctum.geek.nz/?p=282)). Neovim goes further: it removed Vim's modeless `'insertmode'` option altogether ([Neovim vim_diff](https://neovim.io/doc/user/vim_diff.html)).

Shipped configs show the same pattern. **LazyVim, kickstart.nvim and AstroNvim add no insert-mode cursor motions.** LazyVim's only insert-mode Alt maps, `<A-j>`/`<A-k>`, move the *line*, not the cursor, and it adds undo break-points after `, . ;` ([LazyVim keymaps.lua](https://github.com/LazyVim/LazyVim/blob/main/lua/lazyvim/config/keymaps.lua); [kickstart init.lua](https://github.com/nvim-lua/kickstart.nvim/blob/master/init.lua); [AstroNvim mappings](https://github.com/AstroNvim/AstroNvim/blob/main/lua/astronvim/plugins/_astrocore_mappings.lua)). Only NvChad maps `<C-h/j/k/l>` as arrows in insert mode, and doing so overrides the built-in backspace (`i_CTRL-H`) and digraph (`i_CTRL-K`) keys ([NvChad v2.5](https://github.com/NvChad/NvChad/blob/v2.5/lua/nvchad/mappings.lua)). The prominent personal configs checked, ThePrimeagen's and TJ DeVries', have no insert-mode motions. ThePrimeagen's only relevant map makes `<C-c>` a full Esc ([remap.lua](https://github.com/ThePrimeagen/init.lua/blob/master/lua/theprimeagen/remap.lua); [tjdevries keymaps](https://github.com/tjdevries/config.nvim/blob/master/plugin/keymaps.lua)).

The dissenting view is real but limited in scope. In a 2024 r/neovim thread the majority line was "Just don't navigate in insert mode. That's why god invented normal mode", while a minority defended Alt+hjkl, Ctrl+hjkl and readline keys ([r/neovim](https://red.127.pp.ua/r/neovim/comments/1f0tnxe/ditching_arrow_keys_my_biggest_obstacle_is)). The plugins that support that minority still restrict themselves. tpope's vim-rsi refuses to override "important Vim key bindings" ([vim-rsi](https://github.com/tpope/vim-rsi)). mini.basics' `<M-hjkl>` insert motions are off by default, and the stated reason for them is moving "right outside of inserted pairs" ([mini.basics](https://github.com/echasnovski/mini.nvim/blob/main/lua/mini/basics.lua)). There is **no quantitative survey** of these habits, so "majority" here means the weight of threads, docs and shipped configs, not measured usage.

## Every cursor move inside insert splits undo, except `<C-g>U` left/right

The decisive technical point is undo and dot-repeat, because it applies equally to arrows, `<C-o>` and Alt-mapped arrows. Vim documents that for all "special special" keys, which include the arrows, Home/End and `CTRL-O`, "the changes… before and after these keys can be undone separately. Only the last change can be redone and always behaves like an "i" command" ([Vim insert.txt](https://vimhelp.org/insert.txt.html#ins-special-special)). `CTRL-O` "splits undo" too ([insert.txt](https://vimhelp.org/insert.txt.html#ins-special-special)). On Vim 9.x and **released Neovim 0.10–0.12**, an insert-mode arrow therefore behaves exactly like Esc → move → `i` as far as undo and `.` are concerned. Moving inside insert saves at most one keystroke, and the edit is still split.

The one exception is `CTRL-G U`, added in Vim 7.4.849 (2015). It tells Vim "don't start a new undo block with the next left/right cursor movement, if the cursor stays within the same line". The help's own example is `inoremap <Left> <C-G>U<Left>`, so that "using . (redo) will work as expected" ([insert.txt, i_CTRL-G_U](https://vimhelp.org/insert.txt.html#i_CTRL-G_U); [patch 7.4.849](https://git.centos.org/rpms/vim/raw/1eb8d3f8219cf7511626bf40a83ed39c437684b0/f/7.4.849)). This is why autopair plugins use it, and it is the only way to build an insert-mode motion map that does not degrade undo and repeat. It covers **same-line left/right only**. Up/down, word jumps and `<C-o>` motions still split.

Neovim master (after 0.12, unreleased) changes repeat but not undo. `.` now replays the whole insert, including relative cursor moves, while "Undo and |quote.| still restart at each cursor-move" ([Neovim news.txt](https://github.com/neovim/neovim/blob/master/runtime/doc/news.txt); [ins-repeat](https://neovim.io/doc/user/insert.html#ins-repeat)). The release that will ship this could not be confirmed. Until it ships, `<C-g>U` still matters for both undo and repeat. After it ships, `<C-g>U` still matters for undo.

`<C-o>` also has side effects that make it a poor primitive for motion maps. It fires InsertLeavePre/InsertLeave and switches the mode to `niI` ([autocmd.txt](https://vimhelp.org/autocmd.txt.html#InsertLeave); [mode()](https://vimhelp.org/builtin.txt.html#mode%28%29)), which plugins hooked on InsertLeave will see. It can shift the cursor left at end of line ([i_CTRL-O](https://vimhelp.org/insert.txt.html#i_CTRL-O)). It also expands pending abbreviations ([edit.c](https://github.com/vim/vim/blob/master/src/edit.c)). It is fine for an occasional one-shot such as `<C-o>zz` or `<C-o>A`, and poor as the basis for movement keys.

## Cmd+key on this stack is literally Esc+key

On a legacy-encoded terminal, Alt+j is the two bytes `ESC j`, which is identical to pressing Esc and then j. Neovim tells them apart only by timing, through `ttimeoutlen` (default 50 ms) ([options.txt](https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/options.txt); [tmux wiki](https://github.com/tmux/tmux/wiki/Modifier-Keys)). Neovim tries to negotiate the kitty protocol or modifyOtherKeys to remove the ambiguity ([tui.txt](https://raw.githubusercontent.com/neovim/neovim/master/runtime/doc/tui.txt)). With tmux in the path, though, that negotiation is reported not to reach the outer terminal ([claude-code #29129](https://github.com/anthropics/claude-code/issues/29129), reporter's source reading, unverified). Ghostty's `esc:h` keybind action sends a literal ESC followed by h ([Ghostty config reference](https://ghostty.org/docs/config/reference)), so this user's Cmd+H **cannot** be disambiguated by `extended-keys` at all. It is ESC+h by construction.

This race has a documented real case: a tap-Esc/hold-Ctrl Caps Lock, plus tmux, plus Neovim `<A-j>` maps. A quick Caps-tap followed by j fired the Alt map, and the issue was closed with "live with it" ([jaehho/dotfiles #37](https://github.com/jaehho/dotfiles/issues/37)). The user already hit this bug and fixed it by lowering `ttimeoutlen` to 10 ms, which is the mitigation that thread suggested. The current insert-mode `<Nop>` on `<M-h>`/`<M-j>` exists for the same reason. Two consequences follow. First, the 10 ms window is narrow but not zero, so any insert-mode `<M-h/j/k/l>` map is reachable by a fast enough Esc → h/j/k/l, and h/j/k/l are the keys most often typed right after Esc. Second, mapping these keys to motions changes what a misfire does. Today a misfire silently does nothing. With motion maps it moves the cursor while you are still in insert mode, and the next "normal-mode" keystrokes get typed into the buffer. At 10 ms this will be rare. Expanding the set of insert-mode `<M-…>` maps still increases the number of keys where the race can surface.

The habit cost is also close to even. The user's Esc is a single Caps Lock tap that never leaves the home row, which is the setup HN commenters across 2010–2020 call the single most helpful Vim change ([HN 24287951](https://news.ycombinator.com/item?id=24287951); [HN 1295756](https://news.ycombinator.com/item?id=1295756)). For a one-character move, Cmd+L is one chord and Caps, `l`, `a` is three taps. For anything larger, normal mode wins clearly: `f)`, `w`, `A`, `ciw`, `;` all compose and repeat in ways that Cmd+hjkl, pressed repeatedly, cannot. Portability points the same way. Custom insert maps "don't work if you're on a remote server" ([SO 8749998](https://kaweah.freedombox.rocks/kiwix/content/stackoverflow.com_en_all_2023-11/questions/8749998/vim-navigate-on-insert-mode)), and they transfer poorly to emulators ([VSCodeVim #2924](https://github.com/VSCodeVim/Vim/issues/2924)).

## Verdict on A, B and C

| Option | What it buys | What it costs | Verdict |
|---|---|---|---|
| **A** as proposed (Cmd+HJKL arrows, F/B/A/E/D/Z extras, Copilot → Cmd+Shift+K/L) | Arrow-free char/word/line moves in insert | Breaks the freeze; plain `<Left>/<Right>/<Down>/<Up>` and `<C-o>` maps split undo and `.`; 4 more Esc-race keys; Copilot accept moves to a slower chord; Cmd+A loses Ghostty select-all; new Alt keys leak into zsh | Too broad. Not as written |
| **A-minimal** (Cmd+H/L only, as `<C-g>U<Left>`/`<C-g>U<Right>`; Copilot accept-line → Cmd+Shift+L; Cmd+K toggle and Cmd+J `<Nop>` untouched) | Same-line one-char steps (past `)`, `"`, `>`) with undo and `.` intact | Still a freeze override; still two Esc-race keys; Copilot accept-line gets slower | Acceptable after the freeze, only if a measured need remains |
| **B** (keep Copilot keys, movement on Cmd+Shift+HJKL) | Copilot untouched | Cmd+Shift+H is owned by macOS "Hide Ghostty"; four new Ghostty binds; Shift-chords are slower for the most frequent tiny action; same undo issues unless `<C-g>U` | Reject |
| **C** (defer) | Honours the freeze; zero risk; forces the normal-mode habit the sources recommend | Occasional extra keystroke for 1-char moves | **Recommended now** |

The working method, with no config changes, is this. For any move longer than a character or two, or any move across lines, tap Caps (Esc) and use a motion: `f`/`t` with `;`, `w`/`b`/`e`, `A`, `I`, `o`, `gi` to return to the last insert point, or `ciw`/`ci(` instead of navigating and then deleting. Inside insert mode, use `<C-w>` (delete word back), `<C-u>` (delete to start of insert or line), `<C-h>` (backspace), `<C-r>{reg}` (paste), `<C-t>`/`<C-d>` (indent) and `<C-n>`/`<C-p>` (completion). All of these are built in, and Neovim's default `<C-w>`/`<C-u>` already set an undo point first ([Neovim default-mappings](https://neovim.io/doc/user/vim_diff.html#default-mappings)). Use `<C-o>` for a single one-shot such as `<C-o>zz` or `<C-o>A` when the insert is about to end anyway. Commenters put the adjustment at **about three weeks** ([r/neovim](https://red.127.pp.ua/r/neovim/comments/1f0tnxe/ditching_arrow_keys_my_biggest_obstacle_is)), and that fits comfortably before the freeze ends on 2026-12-31.

If the one recurring pain is stepping past an auto-inserted closer, test first whether simply typing the closing character already jumps over it in the current LazyVim autopairs setup. Autopair plugins are built around `<C-g>U` for this reason, so it may need no map at all. If a map is still wanted in January, A-minimal is the version to add, written exactly as `inoremap <M-h> <C-g>U<Left>` / `inoremap <M-l> <C-g>U<Right>`, with matching `<D-h>`/`<D-l>` maps in Neovide. Do not use bare `<Left>`/`<Right>`, do not use `<C-o>` variants, and do not add vertical or word maps.

## Conclusion

The question this user is facing is less "which keys" than "whether insert mode should be a place to move around in". The sources answer no. The undo model enforces that answer more strongly than convention does: every insert-mode move except a same-line `<C-g>U` step is an Esc and an `i` in disguise. The user's own hardware choices, a one-tap Caps-Esc and a 10 ms timeout already tuned against Esc/Alt collisions, have removed most of the problem Alt motion maps were invented to solve. Mapping Cmd+hjkl would re-open the collision surface those settings were set up to close.

The practical implication is to spend the freeze period building the normal-mode reflexes rather than the keymap. At the end of the freeze, decide on evidence: if, after weeks of Caps-Esc, there is still a specific same-line move you keep wishing for, add only that one, with `<C-g>U`. If nothing like that turns up, the current `<Nop>` maps are the right final state.
