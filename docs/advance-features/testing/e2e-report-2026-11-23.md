# Debugger and test runner: E2E test report (2026-11-23)

Branch `fix/debugger-test-runner-e2e`, tested against `main` at `ba53376`. The harness is
in `scripts/e2e/`; its README explains how to rerun it.

## 1. Bottom line

- **31 scenarios** were scripted the way a person uses them: real keystrokes and mouse clicks
  in the real TUI. Each one ran **3 times**, then once more after the last change:
  **114 scenario runs and 562 individual checks**.
- **4 bugs fixed**, each with a regression check that failed before the fix and passes after.
  Startup time is unchanged; none of the changed files load at startup.
- **8 issues flagged, not fixed.** Each is either inside a plugin or would change behaviour,
  so it needs your call. They are listed in §5 and show up in the suites as `[known Fn]` checks.
- **No flaky results** remain. Every non-passing run is a `[known]` check.
- The everyday debugger and test-runner flows all passed in all runs: start, breakpoints,
  stepping, panels, control bar, restart/stop, watches/REPL, Debug Test (Go, Vitest, Jest,
  pytest), results panel, rerun failed, history, coverage. Where they don't match JetBrains
  (§7), the cause is the gaps listed in §5 and §7, not broken features.

**Method:**
- **Input:** keys go through tmux. Clicks and hovers are SGR-1006 mouse escape sequences written
  into the pty, the same bytes a terminal sends.
- **Checks:** state comes over the `--listen` socket (dap session, frames, breakpoints, windows,
  winbars, neotest counts, diagnostics, registers); screen checks use `capture-pane`.
- **Waits:** on conditions, not sleeps.
- **Negative controls:** I broke the code under test on purpose to prove the checks can fail
  (§8).

### Limits of this test: read these before trusting a green result

1. **It ran on Linux, not macOS + Ghostty.** Terminal-specific behaviour was not covered:
   - **Fonts:** Nerd Font glyph widths and fallback. Screenshots were rendered with JetBrains
     Mono, which has no Nerd icons, so icons show as boxes in the PNGs (the terminal itself had
     the right characters).
   - **Option/Meta keys:** your Ghostty `super+…=esc:…` bindings and `macos-option-as-alt`.
   - **Colour space:** Ghostty's `window-colorspace = display-p3`. Colours were checked as
     hex values only.
   - **Ghostty itself:** its own input encoding, CSI-u for `<C-i>`, resize behaviour.
2. **Mouse events are simulated through the terminal's mouse protocol.** This is close to a
   real trackpad but not identical. Not covered: trackpad momentum and smooth scrolling, a
   real double-click interval as Ghostty measures it, drag thresholds, and hover timing (hover
   used two `mouse move` events about 1.5 s apart).
3. **Timing.** The sandbox starts Neovim slower than your Mac (~170 ms vs your ~50 ms). Only
   before/after comparisons are meaningful (§6).
4. **Versions.** Adapters came from Mason and the toolchains are what the sandbox had (§2
   table), so they can differ from yours.
5. **Not covered at all:**
   - C#/.NET (no .NET in the sandbox).
   - Attach (process, port 9229), Django/module configs, `<leader>dx` exception filters.
   - Smart Step Into / Jump to Line / Reset Frame (Node/Python-only features).
   - `e` (edit value), `t` (hide internals) in panels, and REPL completion.
   - `<leader>tw` watch mode, `<leader>ta` attach, `<leader>tH`, `<leader>tca`.
   - Coverage for Vitest/Jest/pytest, and Rust.

## 4. Bugs fixed (in this PR)

### F1: sidebar titles VARIABLES / CALL STACK were never visible
- **Seen:** at the sidebar's fixed 46 columns, the winbar `VARIABLES  dbl-click expand · e edit
  · w watch · y copy` is wider than the window. Neovim cuts a too-wide winbar from the **left**,
  so the panel showed `< dbl-click expand · …` with no title. CALL STACK showed `<ick
  expand/open/switch…`. WATCHES fitted.
- **Fix** (`lua/debugging/layout.lua`): `fit_hint()` keeps only the hint items that fit after
  the title, dropping from the end. It is applied when the panel opens and again on
  `WinResized`, because dap-ui sets the width after `BufWinEnter`.
- **At 46 columns you now see:** `VARIABLES dbl-click expand · e edit` and
  `CALL STACK dbl-click expand/open/switch`. `w watch · y copy` and `t internals · y copy` no
  longer fit there. They come back if the sidebar is wider, and the keys are unchanged.
- **Cost:** a string fit per panel open/resize; nothing on keystrokes or redraws.

### F2: `<leader>dr` opened a second REPL
- **Seen:** LazyVim's `<leader>dr` = `dap.repl.toggle()` opened another REPL split beside the
  tray's REPL. The editor shrank to about a third of its height and the view jumped. Pressing
  it again closed only the extra split.
- **Fix** (`lua/debugging/layout.lua` `focus_repl()`, key in `lua/debugging/plugins/core.lua`,
  README row): it jumps to the tray's REPL, opening the tray if it is closed, and a second press
  jumps back to the code. The layout is unchanged.

### F5: Vitest/Jest inline failure text contained the whole JS stack
- **Seen:** LazyVim's neotest virtual-text format joins every line of the message, so a
  Vitest failure became about 1,500 characters on one line:
  `AssertionError: expected 9 to be 10 … at file:///…/node_modules/@vitest/runner/…:155:11 at …`.
- **Fix** (`lua/plugins/testing.lua`, `ui` consumer): the same compact format, minus JS
  stack-frame lines only (indented `at …` ending in `line:col`, `(<anonymous>)` or `(native)`).
  - Vitest now shows `AssertionError: expected 9 to be 10 // Object.is equality`.
  - Jest now shows `Error: expect(received).toBe(expected) // Object.is equality Expected: 5 Received: 4`.
  - Go and pytest messages are unchanged.
  - The full message is still in the float, `<leader>to` and the Test Results panel.

### F13: misleading Go coverage warning when a test panics
- **Seen:** if any test in the package panics, Go writes a coverage profile with only the
  `mode:` line (checked with go 1.26.3 directly). The warning blamed only "code kept inside a
  _test.go file", so it pointed you at the wrong thing.
- **Fix** (`lua/testing/coverage.lua`): wording only. It now names both causes: a test
  panicked, or the code under test is in a `_test.go` file.

Other observations (no action suggested):
- In Go, step into stops on the function's opening line (`func Add(…) {`, line 3) before the
  first statement. That is Delve's behaviour; GoLand does the same.
- In Node, step out of `greet()` stops on the line after the call: js-debug finishes the
  assignment first. VS Code does the same.
- Right-clicking a bufferline tab closes that buffer (LazyVim's `right_mouse_command`). VS Code
  shows a menu there instead; surprising if you right-click a tab expecting one.
- If Neovim is killed rather than quit, the next start shows Vim's swap-file ATTENTION prompt.
  This is standard Vim behaviour.

## 9. Problems in the test harness itself (not your config)

These were found and fixed in the harness, so they don't cause false reports:
- A stack overflow (E1502) came from my RPC returning a cyclic dap frame table.
- Keys sent less than 50 ms after `:cmd<CR>` were lost (measured: 50 ms lost, ≥120 ms fine). That
  is faster than a person types; the harness now waits 150 ms after `<CR>`.
- Two `<Esc>` sent in one write were read as `<M-Esc>`; the harness now spaces keys 40 ms apart.
- Neovim's server process and its LSPs (vtsls, tsserver) survived killed tmux sessions and
  pushed load to 35 on 2 CPUs, which caused early timeouts. The harness now quits Neovim and
  kills its own process tree. A normal `:qa!` left **no** leaked process: checked for vtsls,
  js-debug, Delve and the debuggee, including quitting while stopped in a session.
- `#dap.sessions()` reports 2 for a single session with id 2. The suites count with `pairs`.
